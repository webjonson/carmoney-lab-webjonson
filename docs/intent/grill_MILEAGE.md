# Лог интервью Grill Me: проверка пробега в решении (MILEAGE)

Дата: 2026-09-28. Режим Grill Me (★ 1.5.1): вопросы по одному, не больше шести,
только те, от ответа на которые зависит реализация. Ответы заказчика фиксируют
семантику правила для `intent_MILEAGE.md`.

## Сверка до вопросов

По протоколу сначала сверился с `docs/setup/code_map.md` (раздел 2 — куда
встанет правило), `docs/plan/plan_MILEAGE.md` (черновик с открытыми вопросами
В1–В4), `backend/config/rules.php` и `backend/src/Domain/`. Не спрашивал то,
что уже видно:

- **Граница 400 000**: «не больше 400 000» = включительно; план уже фиксирует
  400 000 → approve, 400 001 → review.
- **Пробег не указан**: `ApplicationValidator` уже даёт 422 (`mileage ?? -1`
  → ошибка), план сохраняет поведение — такие заявки до решения не доходят.
- **Место реализации**: порог `review_mileage_km => 400000` в `rules.php`,
  понижение approve → review в `AssessmentService` после `decide()`;
  `DecisionEngine` не трогаем.
- **Scope**: план уже перечисляет «Не входит» (фронтенд, БД, `max_mileage_km`,
  README, LOAN-12, CASE-08, feature-тесты).

Расхождение в доках: `plan_MILEAGE.md` утверждает, что `code_map.md` нет, но
файл существует — в intent ссылаться на оба (`code_map.md` + инвентаризация
пробега в `docs/setup/AGENTS.md`).

## Вопросы и ответы

### 1. Reject и пробег (план, В1)

**Вопрос.** Заявка с LTV-решением reject (LTV > 85%) и пробегом 400 001 км:
что должно вернуть новое правило?

- «Оставить reject» — правило только понижает approve до review; шаг 2 плана
  и тест `testKeepsRejectWhenMileageAboveReviewThreshold` уже под это написаны.
- «Заменить на review» — «иначе review» читаем буквально; смягчает кредитную
  политику, переворачивает шаг 2 плана и один тест.

**Ответ: оставить reject** (рекомендованный вариант).

### 2. Потолок валидации 500 000 (план, В2)

**Вопрос.** Сейчас валидатор даёт 422 при пробеге > 500 000
(`max_mileage_km`), то есть новое правило работает только в диапазоне
400 001–500 000. Эту связку оставляем?

- «Оставить 500 000» — не трогать существующую проверку и текст её ошибки
  (вне scope по плану).
- «Поднять/убрать потолок» — любой пробег > 400 000 доходит до решения;
  отдельное решение по существующей валидации, расширение scope.

**Ответ: оставить 500 000** (рекомендованный вариант).

### 3. Причина review в ответе API (план, В4)

**Вопрос.** Нужно ли в ответе API как-то помечать, что review пришло именно
из-за пробега (например, поле `reason`), или достаточно самого решения?

- «Не добавлять» — контракт `/api/ltv` и `/api/applications` не меняется.
- «Добавить поле reason» — меняет структуру ответа `assess()`, возможно
  фронтенд, выходит за пределы плана.

**Ответ: не добавлять** (рекомендованный вариант).

### 4. Пустая строка как пробег (план, В3)

**Вопрос.** Пустая строка в `mileage` (`""` после `(int)`-каста становится 0)
сегодня проходит валидацию как пробег 0. Оставляем как есть?

- «Вне scope» — существующий вар валидатора, к новому правилу отношения не
  имеет (0 ниже порога, решение не меняется); фронтенд закрыт `required`.
- «Чинить в этой задаче» — трогаем `ApplicationValidator`, который план
  явно исключает.

**Ответ: вне scope** (рекомендованный вариант).

## Зафиксированная семантика (итог интервью)

1. Пробег > 400 000 км понижает решение с approve до review; граница
   включительная: 400 000 — ещё approve, 400 001 — уже review. Порог в конфиге
   `rules['vehicle']['review_mileage_km'] => 400000`.
   *(источник: формулировка требования «не больше 400 000», план MILEAGE)*
2. Только понижение: reject не смягчается (LTV-reject + 400 001 → reject),
   review по LTV остаётся review. *(источник: ответ в интервью, В1)*
3. Отсутствующий/невалидный пробег — без изменений: 422 от валидатора, до
   решения не доходит. Потолок `max_mileage_km` = 500 000 остаётся: правило
   реально работает в диапазоне 400 001–500 000, выше — 422.
   *(источник: ответ в интервью, В2; код: `ApplicationValidator.php`)*
4. Контракт API не меняется: без поля `reason`; у пониженной заявки
   `approved_limit = 0`. *(источник: ответ в интервью, В4)*
5. Реализация: понижение в `AssessmentService` после `decide()`; порог — 5-й
   параметр конструктора, передаётся из `AppFactory`; `DecisionEngine` не
   трогаем. *(источник: план MILEAGE / code_map.md — из сверки, не из ответов)*
6. Вне scope: `max_mileage_km` и текст его ошибки, вар «пустая строка →
   пробег 0», фронтенд, БД/миграции, LOAN-12, CASE-08, feature-тесты HTTP,
   README. *(источник: ответ в интервью, В2 и В3; план MILEAGE, «Не входит»)*

Все вопросы В1–В4 из плана закрыты ответами заказчика; открытых вопросов
для intent не осталось.
